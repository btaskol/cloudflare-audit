# 📋 Informe de Seguridad – Cloudflare Worker (Herramienta interna de facturación)

> **Nota**: La autenticación y el control de acceso se gestionan en el perímetro mediante Cloudflare Access / Zero‑Trust (política “Allow selected employees”).  
> Este análisis **no** cubre la ausencia de autenticación ni de control de acceso externo, sino que se centra exclusivamente en el código del Worker y en los riesgos internos que pueden afectar a la confidencialidad, integridad y disponibilidad de la aplicación.

## 2. Detalle de Hallazgos

### 2.1. XSS basado en DOM (innerHTML sin sanitizar)

- **Líneas afectadas**  
  - `runningTotal.innerHTML = lines + ...` (cálculo del total)  
  - `resultDiv.innerHTML = \`<div>Factura generada...</div>\`` (respuesta del endpoint)  
  - `opt.value = \`${p.name} - ${money(p.unitPriceCents)} (${p.productId})\`;` (valor del `datalist`)

- **Problema**  
  Los valores que provienen del backend (`p.name`, `orderRef`, `customerName`, `data.lineItems[*].name`) se insertan directamente en el DOM mediante `innerHTML`. Si cualquiera de esos campos contiene contenido HTML/JS (p. ej. `<script>alert(1)</script>`), el script se ejecutará en el contexto de la página.

- **Impacto**  
  - Robo de tokens de sesión de Cloudflare Access.  
  - Ejecución de acciones en nombre del usuario (p. ej. envío de facturas falsas).  
  - Escalada de privilegios dentro del entorno interno.

- **Referencia OWASP**: A03:2021 – Inyección (XSS)

- **Recomendación**  
  - Utilizar `textContent` o plantillas seguras (p. ej. `DOMPurify` o `escapeHTML`) para cualquier dato que provenga del servidor.  
  - Evitar `innerHTML` salvo que se haya sanitizado explícitamente.  
  - Implementar una **Content‑Security‑Policy** que bloquee la ejecución de scripts inline (`script-src 'self'`).

---

### 2.2. Extracción y uso del ID de producto sin validación robusta

- **Código**  
  ```javascript
  function extractProductId(searchValue) {
    const match = searchValue.match(/\(([^)]+)\)$/);
    return match ? match[1].trim() : null;
  }
  ```

- **Problema**  
  - La extracción depende de que el usuario seleccione una opción del `datalist`. Un atacante puede escribir manualmente cualquier cadena que cumpla el patrón, como `Foo (ID‑9999)`, aunque `ID‑9999` no exista.  
  - El backend `/generate` recibe el `productId` tal cual; si no valida la existencia o la pertenencia a la lista, se pueden crear facturas con IDs arbitrarios, provocando **Inyección de objetos internos** o **Broken Access Control** a nivel de datos.

- **Impacto**  
  - Facturas con productos inexistentes o manipulados.  
  - Posible acceso a datos internos de productos no autorizados.

- **Referencia OWASP**: A01:2021 – Control de acceso roto / A03:2021 – Inyección

- **Recomendación**  
  - Validar en el servidor que el `productId` recibido pertenece a la lista de productos autorizados y que el precio no ha sido alterado.  
  - En el cliente, usar un `<select>` con valores reales (`value="productId"`) y mostrar el nombre como texto, evitando la necesidad de parsear strings.  
  - Añadir una capa de firma o token HMAC para los IDs si se necesita integridad del dato en el cliente.

### 2.3. Falta de cabeceras de seguridad (CSP, X‑Content‑Type‑Options, etc.)

- **Observación**  
  El HTML no incluye ninguna cabecera de seguridad ni meta‑etiquetas que refuercen la política de contenido.

- **Impacto**  
  - Facilita la explotación de XSS, click‑jacking y ataques de tipo MIME‑sniffing.  
  - Reduce la defensa en profundidad.

- **Referencia OWASP**: A06:2021 – Seguridad de configuración

- **Recomendación**  
  - Configurar en el Worker (o en la zona Cloudflare) encabezados como:  
    ```http
    Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
    X-Content-Type-Options: nosniff
    X-Frame-Options: SAMEORIGIN
    Referrer-Policy: strict-origin-when-cross-origin
    ```  
  - Evitar `unsafe-inline` en `script-src` siempre que sea posible.

---

### 2.4. Lógica de negocio únicamente en el cliente

- **Problema**  
  - El cálculo de subtotales, descuentos y totales se hace en el navegador (`updateRunningTotal`).  
  - Un usuario puede modificar los valores de los campos (`line-qty`, `line-discount`) o interceptar la petición y cambiar el JSON enviado a `/generate`.

- **Impacto**  
  - Facturas con totales incorrectos (pérdida de ingresos o sobre‑cobro).  
  - Posible manipulación de descuentos para obtener beneficios indebidos.

- **Referencia OWASP**: A02:2021 – Criptografía rota (por falta de integridad) / A05:2021 – Seguridad de configuración

- **Recomendación**  
  - Realizar **toda** la validación y cálculo crítico en el backend. El cliente solo debe ser una capa de conveniencia.  
  - En el servidor, volver a calcular subtotales, descuentos y aplicar impuestos antes de generar la factura definitiva.  
  - Devolver al cliente únicamente la factura final (PDF/JSON) para visualización.

### 2.5. Mensajes de error que pueden filtrar información interna

- **Código**  
  ```javascript
  const data = await resp.json();
  if (!resp.ok) throw new Error(data.error || 'Algo salió mal');
  ```

- **Problema**  
  - El mensaje `data.error` se muestra directamente al usuario (`resultDiv.textContent = ...`).  
  - Si el backend devuelve trazas o códigos internos, estos se exponen.

- **Impacto**  
  - Revelación de lógica interna, nombres de campos, rutas de API, etc., que pueden ser útiles para un atacante interno.

- **Referencia OWASP**: A10:2021 – Registro y monitoreo insuficientes

- **Recomendación**  
  - Normalizar los mensajes de error antes de enviarlos al cliente (p. ej. “Error al generar la factura”).  
  - Registrar los detalles completos en el servidor y no exponerlos al front‑end.

---

### 2.6. Uso de `parseInt` sin especificar radix

- **Código**  
  ```javascript
  const quantity = parseInt(row.querySelector('.line-qty').value, 10) || 0;
  ```

- **Problema**  
  - En el fragmento original se usaba `parseInt(value)` sin segundo parámetro. En algunos navegadores, valores que empiecen con `0x` o `0` pueden interpretarse como hexadecimal u octal, generando resultados inesperados.

- **Impacto**  
  - Cálculos de cantidad incorrectos, potenciales desbordamientos o facturas con cantidades negativas si se combina con `Math.abs` mal usado.

- **Referencia OWASP**: A01:2021 – Control de acceso roto (por entrada no sanitizada)

- **Recomendación**  
  - Siempre especificar el radix (`parseInt(value, 10)`).  
  - Validar que la cantidad sea un entero positivo antes de enviarla
