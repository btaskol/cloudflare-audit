# 📋 Informe de Seguridad – Cloudflare Worker “Sistema de Facturación”

> **Ámbito:** Análisis estático del código JavaScript/HTML que se ejecuta en el navegador del usuario.  
> **Supuestos:**  
> • El acceso al Worker está protegido por Cloudflare Access / Zero‑Trust (no se evalúa la autenticación).  
> • Sólo se revisa el código fuente entregado al cliente; no se dispone del código del backend (`/products`, `/generate`).  

---

## 1. Resumen Ejecutivo

| Riesgo | Severidad | Comentario breve |
|--------|-----------|------------------|
| **XSS reflejado/inyectado vía `innerHTML`** | **Alta** | Se inserta contenido proveniente del servidor y de los usuarios (p. ej. `orderRef`, `customerName`, `product.name`) directamente con `innerHTML` sin escape. |
| **Falta de CSP y cabeceras de seguridad** | **Media** | No se establecen políticas de contenido, `X‑Frame‑Options`, `X‑Content‑Type‑Options`, `Referrer‑Policy`, etc. |
| **Validación insuficiente del lado cliente** | **Media** | Todas las comprobaciones (formato de referencia, cantidad, descuento) se hacen en el navegador; el backend debe volver a validar. |
| **Posible exposición de datos sensibles** | **Media** | El endpoint `/products` devuelve `unitPriceCents` a cualquier usuario autenticado, lo que podría ser información de precios internos. |
| **CSRF / Falta de token anti‑replay** | **Media** | La petición `POST /generate` se envía sin ningún token anti‑CSRF; si el Access token se comparte (p. ej. en una pestaña distinta) un atacante podría forjar la solicitud. |
| **Inyección de ID de producto mediante regex** | **Baja** | La extracción del ID (`extractProductId`) confía en un formato específico; un valor mal formado podría romper la lógica o generar errores. |
| **Ausencia de registro de eventos de seguridad** | **Baja** | No hay `console.log` ni envío de logs a un endpoint de auditoría; dificulta la detección de abuso. |
| **Posible DoS por carga masiva de productos** | **Baja** | No hay paginación ni límite de tamaño en `/products`; un atacante interno podría saturar la respuesta. |

> **Conclusión:** El mayor riesgo proviene de la forma en que se renderiza contenido dinámico con `innerHTML`, lo que permite **Cross‑Site Scripting (XSS)** tanto reflejado como almacenado (si el backend devuelve datos manipulados). Las demás vulnerabilidades son de menor gravedad pero deben ser mitigadas para cumplir con el **OWASP Top 10** y buenas prácticas de Zero‑Trust.

## 3. Análisis de Código – Puntos Críticos

### 3.1. Uso de `innerHTML` sin escape
```javascript
resultDiv.innerHTML = `
  <div>Factura generada correctamente.</div>
  <div class="order-details">
    Pedido: ${data.orderRef} — ${data.customerName}<br><br>
    ${linesHtml}
    ...
`;
```
- `data.orderRef`, `data.customerName` y `linesHtml` provienen del **backend** pero pueden contener contenido controlado por el usuario (p. ej. un nombre con `<script>`).  
- `linesHtml` se construye concatenando valores de `li.name` (nombre del producto) sin escape.  

**Riesgo:** XSS reflejado o almacenado si el backend no sanitiza.

### 3.2. `runningTotal.innerHTML` con datos del cliente
```javascript
runningTotal.innerHTML = lines +
  `Subtotal: ${money(subtotal)}<br>` +
  (totalDiscounts > 0 ? `Descuentos: -${money(totalDiscounts)}<br>` : '') +
  `<span class="grand-total">Estimado (antes de impuestos): ${money(afterDiscount)}</span>`;
```
- `lines` incluye `p.name` (nombre del producto) que proviene de la lista `/products`. Si un atacante logra inyectar código en el nombre del producto, se ejecutará en el navegador de cualquier usuario que cargue la lista.

### 3.3. Falta de sanitización de entrada del usuario
- Los campos `orderRef`, `customerName`, `line-product-search`, `line-qty`, `line-discount` se envían al backend tal cual.  
- No se aplica **whitelisting** (p. ej. regex para `orderRef`) ni se limita la longitud de los campos.  

### 3.4. Ausencia de cabeceras de seguridad
- El HTML no incluye meta‑tags ni encabezados HTTP que mitiguen XSS, click‑jacking o sniffing.  

### 3.5. Posible exposición de precios internos
- El endpoint `/products` devuelve `unitPriceCents` a cualquier usuario autenticado. Si la política de negocio requiere que sólo ciertos roles vean precios, esto viola el principio de **least privilege**.

### 3.6. CSRF
- La petición `POST /generate` se envía sin token anti‑CSRF. Cloudflare Access protege el perímetro, pero si un usuario autenticado visita una página maliciosa en otro origen, el navegador enviará automáticamente la cookie/token y la solicitud será aceptada.

### 3.7. Manejo de errores
```javascript
if (!resp.ok) throw new Error(data.error || 'Algo salió mal');
```
- El mensaje de error se muestra en `resultDiv` mediante `innerHTML` (potencial XSS si el backend devuelve HTML en `data.error`).  

### 3.8. No hay registro de auditoría
- No se registra en consola ni se envía a un endpoint de logging información como: quién generó la factura, cuántas líneas, etc.

## 4. Recomendaciones de Mitigación

| Acción | Prioridad | Detalle de implementación |
|--------|-----------|----------------------------|
| **Sanitizar/escapar todo contenido antes de usar `innerHTML`** | **Alta** | - Utilizar `textContent` o crear nodos DOM con `document.createElement` y asignar valores mediante `node.textContent`. <br> - Si se necesita HTML (p. ej. formato de moneda), usar una librería de escape como `DOMPurify`. |
| **Aplicar CSP estricta** | **Alta** | - En la respuesta del Worker añadir encabezado `Content‑Security‑Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; object-src 'none';` <br> - Ajustar según recursos externos (p. ej. fuentes). |
| **Añadir cabeceras de seguridad** | **Alta** | `X-Frame-Options: DENY` <br> `X-Content-Type-Options: nosniff` <br> `Referrer-Policy: strict-origin-when-cross-origin` <br> `Permissions-Policy: interest-cohort=()` |
| **Validación y saneamiento del lado servidor** | **Alta** | - Verificar que `orderRef` cumpla con un patrón (p. ej. `/^PED-\d{4,}$/`). <br> - Limitar longitud de `customerName` (máx. 100 chars). <br> - Re‑calcular precios y descuentos en el backend, ignorando cualquier cálculo enviado por el cliente. |
| **Implementar token anti‑CSRF** | **Media** | - Generar un token único por sesión (por ejemplo, mediante `Access` JWT claims) y enviarlo como encabezado `X-CSRF-Token` en la petición `POST /generate`. <br> - El backend debe validar que el token coincida. |
| **Escapar nombres de productos en `/products`** | **Media** | - Sanitizar `p.name` antes de enviarlo al cliente (p. ej. reemplazar `<`, `>`, `&`). |
| **Limitar exposición de precios** | **Media** | - Si no es necesario que todos los empleados vean `unitPriceCents`, mover esa información a un endpoint protegido por roles o eliminarla del listado público. |
