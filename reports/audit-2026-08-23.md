# 📋 Informe de Seguridad – Cloudflare Worker (Aplicación Interna)

> **Alcance**: Análisis del código HTML + JavaScript que constituye la UI del Worker y de los endpoints `/products` y `/generate` que se invocan desde el cliente.  
> **Entorno**: Aplicación interna de facturación, accesible **solo** para empleados de la empresa.  
> **Objetivo**: Detectar vulnerabilidades (OWASP Top 10 y controles internos), exposición de secretos y deficiencias en la validación de origen de las peticiones.

---

## 1️⃣ Resumen de Riesgos

| Riesgo | Severidad | Comentario breve |
|--------|-----------|------------------|
| **Ausencia de autenticación / autorización** | **ALTO** | Cualquier usuario con la URL del Worker puede obtener la lista de productos y generar facturas. |
| **Falta de verificación de origen (IP/Headers)** | **ALTO** | No hay controles que limiten el acceso a la red interna o a usuarios autenticados. |
| **CSRF (Cross‑Site Request Forgery)** | **ALTO** | El endpoint `/generate` acepta peticiones POST sin token anti‑CSRF ni SameSite = Strict. |
| **Inyección de datos en la UI (XSS Reflejado/Almacenado)** | **MEDIO** | Los valores devueltos por `/generate` se insertan en `innerHTML` sin sanitizar. |
| **Exposición de datos sensibles en la respuesta** | **MEDIO** | Se devuelven precios en centavos y IDs de producto sin filtrar; si el Worker se expone, se filtran datos internos. |
| **Validación insuficiente de los datos de entrada** | **MEDIO** | No se valida que `productId` pertenezca a la lista de productos autorizados; posible **IDOR** (Insecure Direct Object Reference). |
| **Manejo de errores y logging en cliente** | **BAJO** | No hay `console.log` que revele secretos, pero la ausencia de logs de auditoría en el Worker dificulta la detección de abusos. |
| **Uso de `fetch` con rutas relativas** | **BAJO** | Si el Worker se despliega en un dominio público, los navegadores pueden enviar peticiones a cualquier origen que coincida con la ruta, facilitando ataques de **CORS** mal configurado. |
| **Dependencia de datos estáticos en el cliente** | **BAJO** | Los precios y IDs se cargan en el cliente; un atacante podría modificar el DOM y enviar precios alterados al backend si éste no vuelve a validar. |

## 2️⃣ Detalle de Vulnerabilidades

### 2.1 Control de Acceso (OWASP‑A01: Broken Access Control)

| Evidencia | Impacto |
|-----------|---------|
| No existe ningún mecanismo de autenticación (cookies, JWT, API keys, Mutual TLS, etc.). | Un atacante externo que descubra la URL del Worker puede listar productos y crear facturas falsas. |
| No se verifica la procedencia de la petición (IP interna, encabezado `CF-Connecting-IP`, `X-Forwarded-For`, etc.). | Cualquier origen de Internet puede consumir los endpoints. |
| Los endpoints `/products` y `/generate` están expuestos como rutas públicas del Worker. | Violación de la política “solo empleados”. |

### 2.2 CSRF (OWASP‑A08: Software and Data Integrity Failures)

* El formulario envía un `POST` a `/generate` sin token anti‑CSRF.  
* El navegador enviará automáticamente cookies (si se añaden en el futuro) y encabezados de autenticación, permitiendo que un sitio malicioso haga que un empleado genere facturas sin su consentimiento.

### 2.3 Inyección / XSS (OWASP‑A07: Cross‑Site Scripting)

```js
resultDiv.innerHTML = `
  <div>Factura generada correctamente.</div>
  <div class="order-details">
    Pedido: ${data.orderRef} — ${data.customerName}<br><br>
    ${linesHtml}
    ...
`;
```

* `data.orderRef`, `data.customerName` y `linesHtml` provienen directamente del cuerpo de la respuesta del Worker.  
* Si el backend no sanitiza estos campos, un atacante podría inyectar `<script>` o atributos `onerror` y ejecutar código en el navegador del empleado (XSS reflejado o almacenado).

### 2.4 Inseguro Direct Object Reference (IDOR) – OWASP‑A04

* El cliente extrae el `productId` del texto del `datalist` (`"${p.name} - ${money(p.unitPriceCents)} (${p.productId})"`).  
* No hay verificación en el backend de que el `productId` enviado realmente corresponda a un producto autorizado para ese usuario.  
* Un atacante podría modificar el valor del campo y enviar un ID de producto inexistente o de otro cliente, provocando facturas con precios arbitrarios.

### 2.5 Falta de Validación de Entrada (OWASP‑A02: Cryptographic Failures / OWASP‑A03: Injection)

* Los campos `quantity` y `discountPercent` se convierten a `int` / `float` sin validar rangos máximos (p.ej., `quantity` = 10 000 000).  
* No se controla que el descuento no supere el 100 % (aunque el `max` del input lo limita, el cliente puede forzar valores mediante herramientas de desarrollo).  

### 2.6 Exposición de Información Sensible

* La lista de productos incluye precios en centavos y IDs internos. Si el Worker se vuelve accesible fuera de la red corporativa, se filtran datos de precios y catálogos internos.  
* No hay enmascaramiento ni limitación de campos en la respuesta de `/generate`.

### 2.7 Logging y Manejo de Errores

* No se usan `console.log` que expongan secretos, lo cual es positivo.  
* Sin embargo, la ausencia de **logs de auditoría** en el Worker (p.ej., registro de quién generó la factura, IP, timestamp) dificulta la detección de abuso interno o externo.

### 2.8 Configuración CORS

* No se muestra la configuración del Worker, pero al usar rutas relativas (`fetch('/products')`) el Worker responderá a cualquier origen que pueda cargar la página.  
* Si el Worker no establece encabezados `Access-Control-Allow-Origin` restrictivos, cualquier sitio externo podrá leer la lista de productos mediante una petición `fetch` desde el navegador (Data Leakage).

## 3️⃣ Recomendaciones de Mitigación

| Acción | Prioridad | Cómo implementarla (ejemplo) |
|--------|-----------|------------------------------|
| **1. Autenticación y autorización** | **ALTA** | - Añadir verificación de JWT, API‑Key o Mutual TLS en cada request del Worker.<br>- Utilizar `request.headers.get('Authorization')` y validar contra un Identity Provider interno.<br>- Restringir rutas a usuarios con rol *empleado*. |
| **2. Restricción de origen (IP / VPC)** | **ALTA** | - En el Worker, comprobar `request.headers.get('CF-Connecting-IP')` contra una lista blanca de rangos internos.<br>- O bien, desplegar el Worker detrás de un túnel privado (Cloudflare Access, Zero‑Trust). |
| **3. Protección CSRF** | **ALTA** | - Generar un token CSRF en la carga inicial (`GET /`) y enviarlo como cookie `SameSite=Strict` + encabezado `X-CSRF-Token` en el `POST /generate`.<br>- Validar el token en el Worker antes de procesar la factura. |
| **4. Sanitizar salida HTML** | **MEDIA** | - Usar `textContent` para valores simples y una librería de escape (p.ej., `DOMPurify`) para `linesHtml`.<br>- Evitar `innerHTML` con datos no confiables. |
| **5. Validación de `productId` en el backend** | **MEDIA** | - En el Worker, buscar el `productId` en la base de datos o en la lista de productos cargada y rechazar si no coincide.<br>- No confiar en el ID enviado por el cliente. |
| **6. Validar rangos de `quantity` y `discountPercent`** | **MEDIA** | - En el Worker, aplicar reglas: `1 ≤ quantity ≤ maxQty` y `0 ≤ discountPercent ≤ 100`.<br>- Devolver error 400 si se violan. |
| **7. Limitar la información devuelta** | **MEDIA** | - En `/products`, devolver solo `productId`, `name` y `unitPriceCents` si es necesario; ocultar campos internos.<br>- En `/generate`, excluir campos que no sean necesarios para la UI (p.ej., `costPrice`). |
| **8. Añadir logs de auditoría** | **BAJA** | - Registrar en Cloudflare Logs o en un bucket de almacenamiento: `userId`, `IP`, `orderRef`, `timestamp`, `status`. |
| **9. Configurar CORS restrictivo** | **BAJA** | - En el Worker, responder con `Access-Control-Allow-Origin: https://intranet.ejemplo.com` (o `null` si solo se usa desde la misma zona). |
| **10. Seguridad en el cliente** | **BAJA** | - Desactivar `autocomplete` en campos sensibles (ya está hecho).<br>- Añadir `inputmode="numeric"` y `pattern` para reforzar la validación del navegador. |

## 4️⃣ Checklist rápido para el despliegue

| ✅ | Acción |
|----|--------|
| ☐ Implementar autenticación (JWT, API‑Key, Mutual TLS). |
| ☐ Verificar origen IP / usar Cloudflare Access. |

| ☐ Sanitizar cualquier dato que se inserte con `innerHTML`. |
| ☐ Validar `productId` contra la lista de productos en el backend. |
| ☐ Limitar la exposición de precios y IDs en `/products`. |
| ☐ Registrar eventos críticos (quién genera factura, cuándo, IP). |
| ☐ Configurar encabezados CORS restrictivos. |
| ☐ Revisar y probar límites de `quantity` y `discountPercent`. |
| ☐ Realizar pruebas de penetración internas (OWASP ZAP, Burp) antes de producción. |

---

## 5️⃣ Conclusión

Aunque el código cliente no muestra `console.log` ni secretos explícitos, **la mayor vulnerabilidad es la ausencia de controles de acceso y de protección CSRF**, lo que convierte a la aplicación en un objetivo fácil para cualquier actor externo que descubra la URL del Worker. Además, la inserción directa de datos en el DOM sin sanitizar abre la puerta a XSS, y la falta de validación de `productId` permite posibles IDOR.

Aplicar las mitigaciones listadas reducirá drásticamente el riesgo y alineará la solución con los requisitos de seguridad de una aplicación interna corporativa.
