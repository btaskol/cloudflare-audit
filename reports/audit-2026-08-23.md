## Auditoría de Seguridad del código entregado  
**Proyecto:** “Sistema de Facturación” (HTML + JavaScript que se ejecuta en un Cloudflare Worker).  
**Alcance:** Sólo se ha recibido el código del *frontend* (HTML + JS). Los endpoints `/products` y `/generate` se asumen implementados en el Worker, por lo que la auditoría incluye también los riesgos que esos endpoints pueden introducir aunque no se haya visto su código.

---

## 1. Resumen ejecutivo  

| Área | Riesgo | Severidad* | Comentario breve |
|------|--------|------------|------------------|
| **XSS (reflejado / almacenado)** | Uso de `innerHTML` con datos provenientes del servidor (lista de productos, respuesta de `/generate`). | **Alta** | Si el servidor devuelve datos no sanitizados (p. ej. nombre de producto con `<script>`), el atacante puede ejecutar código en el navegador del usuario. |
| **CSRF** | Los formularios envían peticiones `POST` a `/generate` sin token anti‑CSRF. | **Media** | Un sitio externo podría forzar la generación de facturas si el usuario está autenticado (aunque no haya autenticación explícita, el Worker podría usar cookies o tokens). |
| **Inyección de datos** | No hay validación estricta del payload enviado a `/generate`. | **Media** | Un cliente malicioso puede enviar `productId` arbitrario, cantidades negativas, o descuentos > 100 % y forzar cálculos erróneos o sobrecargar la lógica del Worker. |
| **Exposición de información** | La lista completa de productos se entrega sin restricción. | **Baja** | Dependiendo del negocio, exponer precios y IDs puede ser información sensible. |
| **Denegación de Servicio (DoS)** | No hay limitación de tamaño de cuerpo ni de número de líneas de producto. | **Media** | Un atacante puede enviar miles de ítems y agotar recursos del Worker. |
| **Falta de cabeceras de seguridad** | No se establecen CSP, HSTS, X‑Content‑Type‑Options, Referrer‑Policy, etc. | **Media** | Reduce la defensa en profundidad contra XSS, click‑jacking y ataques de protocolo. |
| **Manejo de errores** | Los mensajes de error se imprimen directamente en el DOM sin sanitizar. | **Baja** | Podría revelar información interna del Worker (p. ej. stack traces). |
| **Uso de `fetch` sin `await` en `loadProducts`** | Si la petición falla, el UI queda sin productos y sin control de reintentos. | **Baja** | No es un riesgo de seguridad, pero afecta la disponibilidad. |

\*Se usa la escala **Baja / Media / Alta** según el impacto potencial y la facilidad de explotación.

## 2. Detalle de los hallazgos

### 2.1. Front‑end (HTML + JS)

| Línea / fragmento | Problema | Impacto | Evidencia |
|-------------------|----------|---------|-----------|
| `datalist.innerHTML = ''` + `opt.value = `${p.name} - ${money(p.unitPriceCents)} (${p.productId})`;` | Los valores del `datalist` se insertan sin escape. Si `p.name` contiene caracteres HTML, el navegador los interpreta como parte del markup del `<option>`. | XSS almacenado (si el backend permite nombres con HTML). | `innerHTML` no se usa aquí, pero el `value` de `<option>` sí puede contener `<` y `>` que el navegador mostrará como texto, sin embargo, más adelante se usa `innerHTML` para renderizar la lista de productos en `runningTotal`. |
| `runningTotal.innerHTML = lines + ...` | `lines` se construye concatenando `p.name` y valores numéricos sin escape. | XSS reflejado. | Si el nombre del producto contiene `<script>`, se ejecutará cuando se actualice el total. |

| No hay límite de número de líneas (`addLineItem` permite crear indefinidamente). | Un usuario malintencionado puede crear cientos de ítems y saturar la petición. | DoS. | — |

### 2.2. Supuestos del Worker (endpoints `/products` y `/generate`)

Aunque no se ha visto el código del Worker, el frontend revela varios supuestos que deben revisarse:

| Supuesto | Riesgo si no se controla |
|----------|--------------------------|
| **`/products` devuelve JSON con campos `productId`, `name`, `unitPriceCents`** | Si el JSON proviene de una base de datos sin sanitizar, un atacante que logre insertar HTML en `name` o `unitPriceCents` (p. ej. mediante una vulnerabilidad de inyección en la base de datos) podrá explotar XSS en el cliente. |
| **`/generate` recibe `{orderRef, customerName, lineItems}`** | No hay validación de tipos, rangos ni de existencia del `productId`. Un atacante puede: <br>• Enviar `productId` inexistente → error o comportamiento inesperado.<br>• Enviar `quantity` negativa → descuentos o totales incorrectos.<br>• Enviar `discountPercent` > 100 → total negativo.<br>• Inyectar código en `orderRef` o `customerName` que luego se incluya en la respuesta HTML sin escape. |
| **Respuesta de `/generate` incluye `lineItems` con `name`, `unitPriceCents`, `discountAmountCents`** | Si el Worker devuelve directamente los valores recibidos (p. ej. `orderRef`), cualquier contenido malicioso será reflejado en `resultDiv.innerHTML`. |
| **No hay autenticación / autorización** | Si el Worker está expuesto públicamente, cualquiera puede generar facturas y consumir recursos. |
| **No hay limitación de tamaño de cuerpo** | Un atacante puede enviar un payload de varios MB, agotando la cuota de CPU/Memory del Worker y provocando un **Rate‑Limit** o **DoS**. |
| **No se controla la tasa de peticiones** | Un atacante puede lanzar cientos de peticiones a `/generate` y agotar el límite de 1000 req/s por cuenta de Cloudflare. |
| **No se establecen cabeceras de seguridad en la respuesta** | El Worker debería devolver `Content‑Security‑Policy`, `X‑Content‑Type‑Options: nosniff`, `X‑Frame‑Options: DENY`, `Strict-Transport-Security`, etc. |

## 3. Recomendaciones de mitigación

### 3.1. En el Front‑end (HTML + JS)

| Acción | Por qué | Cómo implementarlo |
|--------|---------|--------------------|
| **Escapar siempre los datos antes de insertarlos en el DOM** | Evita XSS. | - Reemplazar `innerHTML` por `textContent` siempre que sea posible.<br>- Cuando sea necesario usar `innerHTML` (p. ej. para formatear líneas con `<br>`), sanitizar con una librería como **DOMPurify**.<br>- Ejemplo: `runningTotal.innerHTML = DOMPurify.sanitize(lines + ...)`. |
| **Usar plantillas seguras** | Reduce errores de concatenación. | - Utilizar `template` HTML y `cloneNode(true)`.<br>- O bien usar `String.raw` con placeholders escapados. |
| **Validar y normalizar la entrada del usuario** | Evita que datos fuera de rango lleguen al servidor. | - En `addLineItem`, limitar `quantity` a `>= 1` y `discountPercent` a `0‑100`.<br>- Mostrar mensajes de error antes de enviar. |
| **Implementar token anti‑CSRF** | Protege contra peticiones forjadas. | - Generar un token aleatorio en el Worker (por ejemplo, en una cookie `HttpOnly; SameSite=Strict`) y enviarlo como encabezado `X-CSRF-Token` en la petición `POST`. |
| **Establecer cabeceras de seguridad en la respuesta** | Refuerza la defensa en profundidad. | - En el Worker, añadir: <br>`Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; object-src 'none';`<br>`X-Content-Type-Options: nosniff`<br>`X-Frame-Options: DENY`<br>`Referrer-Policy: same-origin`<br>`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload` |
| **Limitar número máximo de líneas** | Evita DoS por uso excesivo de memoria. | - Definir una constante, p. ej. `MAX_LINE_ITEMS = 20;` y bloquear la creación de más. |
| **Manejo de errores sin revelar información interna** | No dar pistas a atacantes. | - Mostrar mensajes genéricos al usuario (`"Error al procesar la solicitud"`).<br>- Loggear detalles en el Worker (solo en consola o en un sistema de logs). |
| **Usar `fetch` con `credentials: 'same-origin'` y `mode: 'same-origin'`** | Asegura que solo se envíen cookies de la misma zona y evita CORS inesperado. | ```js\nawait fetch('/generate', {\n  method: 'POST',\n  credentials: 'same-origin',\n  headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': csrfToken },\n  body: JSON.stringify(payload)\n});\n``` |
| **Implementar un “fallback” de carga de productos** | Mejora la disponibilidad. | - Reintentar `loadProducts()` con back‑off exponencial si falla.<br>- Mostrar mensaje amigable al usuario. |
